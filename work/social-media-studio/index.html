Case 2 · FlyRank backend capstone

One blog post in, one campaign out, and every post published exactly once

Python · FastAPI · SQLAlchemy · APScheduler · Ollama 14 tests pass View the repo

Context

Turn one blog post into platform-specific social posts for Mastodon, X and LinkedIn, let a person approve them, then publish each one on schedule.

Constraint

A retry after a timeout must not make a second post. Publishing to a real account is irreversible, so a crash at the worst moment, after the post went out but before it was marked done, can't be allowed to duplicate it.

What I did

  • Rules in code, not in hope: each generated variant is checked against its platform's profile (length, tone, hashtag count). A variant that breaks a rule is blocked with an error naming the rule and never reaches review.
  • A human gate: only an approved variant can be scheduled. Scheduling anything else is refused with an explicit 4xx.
  • A durable, idempotent scheduler: the worker claims each due slot atomically, and every publish is guarded by an idempotency key checked before any adapter is called. A recovery pass returns stale slots after a crash.

Evidence

Outcome

One slot is always one post. Which adapter backs a platform (the real Mastodon client or a recording mock) is a config setting, not a code path, so the same guarantees hold in tests and in production.
